# Approach

**One engine, three surfaces.** `ProcurementEngine.process(batch)` is a pure function of (PR rows, master data, contracts, active `Policy`). The batch API, the chat (a single PR evaluated together with earlier chat PRs) and the buyer workspace all call it, so a PR gets the same decision wherever it comes from.

## Pipeline per Batch

Validate rows (`NOT_PROCESSED` with a stated reason for bad quantity, date, plant or duplicate line) → resolve items (code, else token-based description match with synonyms and mandatory spec tokens such as `6308`, `M10x40`; vague text becomes NEW, never a guessed item) → club lines (same item+plant, creation window, need-by window, earliest eligible requirement, NEW never clubbed) → per requirement: value (contract rate if a contract has ceiling left, else lowest contract rate, else latest PO ≤365d, else standard price) → decision chain → consolidate POs (same supplier, plant, route, within window).

## Contracts

Register contracts and PDF-only contracts are one pool. A contract is usable if it covers the item, is valid on the requirement date, its supplier is Active and ceiling-left ≥ qty × rate. Ceilings are consumed in requirement order, only by requirements that really become `CONTRACT_PO`.

PDF schedules are parsed from the PDF text; buyers can add PDFs or enter contracts by hand.

## Preferred Suppliers

Active suppliers with a PO or a contract for the item in the 548 days before the date; score = frequency 35%, recency 25%, contract history 15%, on-time 15%, quality 10%; reference price = latest PO price, else contract rate.

Sourcing suggestions = preferred first, then Active suppliers of the item's category ranked by equal-weight on-time + quality, up to the route's count (RFQ 3, RFP 5, Capex 5). Every score is explained in the preferred-supplier API.

## Policy as Data

The active `Policy` (numbers, capex types, extra rules) is stored as JSON in SQLite (`policy_versions`) and mirrored in `data/policies/`. `policy_parse.py` turns a document into proposed values plus a plain-language diff; Procurement edits version/date and approves; the engine is rebuilt from the new version.

This allows policy amendments to change procurement decisions without modifying the decision-engine code.

## Auditability

Each row's `reason` names the clause, the valuation basis (contract/PO/standard price) and the supplier choice; approvals, overrides (with mandatory written reason, original decision stored), policy activations, contract additions and PR creation are written to an `actions` table with actor and time.

## AI Tools Used

I used **ChatGPT (GPT-6)** and **Claude** as development assistants during the implementation of this challenge.

They were used for:
- Discussing and validating the procurement-policy implementation approach.
- Assisting with code generation, debugging, and refactoring.
- Reviewing backend APIs, frontend behavior, and implementation details.
- Designing and checking edge cases for item matching, policy amendments, contracts, supplier selection, and chat-based PR creation.
- Reviewing documentation and deployment considerations.
- Assisting with test-case design and validation of the application's expected behavior.

The procurement decisions themselves are generated by the application's implemented `ProcurementEngine` and policy data. AI tools were used as development aids and are not runtime decision-makers for procurement routing.
